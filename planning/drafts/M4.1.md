## Outcome

A launch is tracked from process creation through exit, including descendants, timeout and cancellation.

## Milestone

#4

## Dependencies

#2, #3

## Scope

- Launch argument vectors without an implicit shell using normalized cwd, final application PATH and protected environment construction; allocate logs and an application ID before observable side effects where possible.
- Track kernel-backed process identities, exit status and ordinary descendants using a documented reliable ownership mechanism; retain handles/results if subsequent processing or the client connection fails. Expose retention hooks for the real window waits implemented in M4.3.
- Enforce one active application per session, including tracked living descendants; allow its dialogs and a later sequential launch after the tracked process set exits. Extend the fixture with exits, delayed windows and descendants.

## Acceptance criteria

- [ ] Different-cwd tests verify executable paths, bare PATH lookup, argv boundaries, explicit allowed environment overrides and durable stdout/stderr logs.
- [ ] A simulated post-launch wait failure, cancellation and a disconnected real launch retain the application/process handle and known side effects in records; no automatic launch retry occurs. Real compositor window-timeout acceptance belongs to M4.3, after discovery/waits exist.
- [ ] A second launch while the first app or its descendants remains live fails before spawning; a later launch after complete exit succeeds. Ownership records cannot become signaling authority for a reused PID.
